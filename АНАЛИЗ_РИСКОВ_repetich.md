## 1. Краткое описание системы

Настольное JavaFX-приложение с двухролевой моделью доступа:

| Роль | Способ получения | Возможности |
|---|---|---|
| `ADMIN` | Логин/пароль `admin`/`admin`, зашитые в код (`ConnectionUtil.java:11–12`) | Полный CRUD товаров и пользователей |
| `USER` | Запись в таблице `polzovateli` | Просмотр таблицы товаров, поиск |

**Структура:**

```
Launcher → HelloApplication → HelloController (авторизация)
                                    ↓
                                 Menu (хаб)
                    ┌───────────────┴───────────────┐
              Tabltovar (товары)              TablPolz (пользователи, только ADMIN)
                    └───────────────┬───────────────┘
                          ConnectionUtil (JDBC, статические методы)
                                    ↓
                          MySQL 192.168.1.141:3306/toor11
```

**Ключевые классы:**

## 4. Детальный разбор рисков

### 4.1 Критические риски

#### R-01 · NullPointerException при недоступной БД → аварийное завершение
**R = 5 × 5 = 25 · Категория: Устойчивость**

**Описание.** Паттерн `try-with-resources` используется с ресурсом, который может быть `null`. В Java спецификация требует, чтобы ресурс был `final` или «эффективно финальным», но **не проверяет на `null` до вызова `.close()`** — проверка происходит в сгенерированном `finally`-блоке уже после того, как тело `try` бросило исключение.

**Механизм отказа (`ConnectionUtil.java:40–42`):**

```java
public static String authorize(String login, String password) {
    // ...
    try (Connection conn = ConnectDb();                              // возвращает null при ошибке
         PreparedStatement pstmt = conn.prepareStatement(sql)) {     // ← NPE ЗДЕСЬ
        if (conn == null) return null;                               // ← НЕДОСТИЖИМО
        // ...
    } catch (SQLException e) { ... }                                 // ← NPE НЕ ЛОВИТСЯ
}
```

1. БД недоступна → `ConnectDb()` перехватывает `SQLException`, вызывает `showAlert(...)` и **возвращает `null`**.
2. `conn.prepareStatement(sql)` вызывается на `null` → `NullPointerException`.
3. `catch (SQLException e)` **не перехватывает** NPE — исключение выходит из метода.
4. Строка `if (conn == null) return null;` находится **после** вызова `prepareStatement` и физически недостижима.
5. Исключение пробегает через `HelloController.voiti_button()` (там тоже нет `catch`) → до обработчика JavaFX → **диалоговое окно ошибки и остановка приложения**.

**Затронутые участки (9 из 10 методов доступа к данным):**

| Файл:строка | Метод |
|---|---|
| `ConnectionUtil.java:40–42` | `authorize()` |
| `ConnectionUtil.java:57–59` | `getDataUsers()` |
| `ConnectionUtil.java:81–82` | `addUser()` |
| `ConnectionUtil.java:100–101` | `updateUser()` |
| `ConnectionUtil.java:119–120` | `deleteUser()` |
| `ConnectionUtil.java:134–136` | `getPolzovateli()` |
| `ConnectionUtil.java:160–161` | `addPolzovatel()` |
| `ConnectionUtil.java:181–182` | `updatePolzovatel()` |
| `ConnectionUtil.java:202–203` | `deletePolzovatel()` |

В методах `addUser`, `updateUser`, `deleteUser`, `addPolzovatel`, `updatePolzovatel`, `deletePolzovatel` проверки `conn == null` нет **вовсе**.

**Дополнительный дефект.** В `getDataUsers()` и `getPolzovateli()` проверка `if (conn == null) return list;` формально есть, но недостижима — вызывающий код получит не пустой список, а исключение.

**Дополнительный дефект.** `showAlert()` в `ConnectDb()` вызывается **до** того, как будет предпринята попытка `conn.prepareStatement`. При множественных вызовах подряд (см. R-06) пользователь получит лавину модальных окон.

**Последствия.** Полная потеря работоспособности при любом сетевом сбое — самом вероятном отказе в клиент-серверном приложении.

**Меры снижения:**
1. Проверять `conn == null` **до** входа в `try-with-resources`, либо вынести её в отдельный метод-обёртку.
2. Перехватывать `SQLException | RuntimeException`.
3. Централизовать подключение в `try (Connection c = requireConnection()) { ... }`.
4. Добавить `Thread.setDefaultUncaughtExceptionHandler` (см. R-26).

#### R-02 · Вход администратора по учётной записи `admin`/`admin` из исходного кода
**R = 5 × 5 = 25 · Категория: Безопасность**

**Описание.** Полные права администратора выдаются при совпадении логина и пароля с константами, объявленными в исходном коде.

**Механизм (`ConnectionUtil.java:11–12`, `35–37`):**

```java
private static final String ADMIN_LOGIN = "admin";
private static final String ADMIN_PASSWORD = "admin";
// ...
if (ADMIN_LOGIN.equals(login) && ADMIN_PASSWORD.equals(password)) {
    return "ADMIN";
}
```

**Последствия:**
- **Полный обход системы разграничения доступа.** Любой пользователь приложения вводит `admin`/`admin` и получает CRUD всех товаров и пользователей, включая чтение и изменение паролей (см. R-04).
- **Невозможность отозвать доступ** — учётная запись зашита в бинарный файл, её нельзя отключить ни удалением из БД, ни изменением данных.
- **Коллизия с доменными данными.** Если в таблице `polzovateli` существует пользователь с `login = 'admin'`, он не сможет войти как `USER` — условие на строке 35 срабатывает раньше проверки БД.
- **Неизбежность причинения вреда (P = 5).** Учётные данные видны в любом декомпиляторе (javap, CFR, IntelliJ) и в исходнике, попадающем в репозиторий.

**Меры снижения:**
1. Удалить константы `ADMIN_LOGIN`/`ADMIN_PASSWORD`.
2. Добавить в таблицу `polzovateli` столбец `role ENUM('ADMIN','USER') NOT NULL DEFAULT 'USER'`.
3. Реализовать авторизацию запросом `SELECT id, role FROM polzovateli WHERE login = ? AND parol_hash = ?` и возвращать фактическую роль из БД.
4. Убрать `exports com.example.repetich;` из `module-info.java` (см. R-30).

#### R-03 · Учётные данные БД и сетевой адрес зашиты в исходный код
**R = 4 × 5 = 20 · Категория: Безопасность**

**Описание.** Строка подключения содержит хост, порт, имя базы, логин и пароль пользователя MySQL.

**Механизм (`ConnectionUtil.java:18–22`):**

```java
Connection conn = DriverManager.getConnection(
        "jdbc:mysql://192.168.1.141:3306/toor11",
        "toor11",
        "toor11"
);
```

**Последствия:**
- Учётная запись БД имеет неограниченные права (не видно `GRANT`-ограничений; имя пользователя совпадает с именем БД — типичный шаблон «создал БД → выдал ALL»).
- **Компрометация приложения равносильна компрометации всей БД.** Имя `toor11` указывает на учебную базу данных ПМИ/PМИ-группы; при публикации работы это раскрывает инфраструктуру.
- Компрометация при публикации репозитория, выгрузке в архив или передаче `.jar`.

**Меры снижения:**
1. Вынести в `db.properties` (вне VCS) или переменные окружения:
   ```
   DB_URL=jdbc:mysql://%s:%s/%s
   DB_USER=
   DB_PASS=
   ```
2. В `pom.xml` добавить фильтрацию ресурсов, исключающую `.properties` из сборки.
3. Выдать отдельного пользователя БД с минимальными привилегиями:
   ```sql
   CREATE USER 'repetich_app'@'%' IDENTIFIED BY '<сложный пароль>';
   GRANT SELECT, INSERT, UPDATE, DELETE ON toor11.* TO 'repetich_app'@'%';
   -- без DROP, ALTER, FILE, GRANT
   ```
4. Валидировать, что пароль не содержит имени пользователя.

#### R-04 · Пароли хранятся и отображаются в открытом виде
**R = 5 × 5 = 25 · Категория: Безопасность**

**Описание.** Три независимых дефекта в одном сценарии — пароль пользователя виден в БД, в таблице и в поле ввода на экране редактирования.

**Механизм:**

**(а) Открытый текст в БД.** Поле называется `parol`, сравнение прямолинейное (`ConnectionUtil.java:38`):
```java
String sql = "SELECT id FROM polzovateli WHERE login = ? AND parol = ?";
```
Колонка `parol` не является хешем.

**(б) Выборка пароля в список (`ConnectionUtil.java:131–149`):**
```java
String sql = "SELECT id, name, family, login, parol FROM polzovateli";
```
Пароли всех пользователей загружаются в память клиента, даже если текущий пользователь — обычный `USER` с правами только на просмотр товаров.

**(в) Отображение в UI.** В `tablpolz.fxml` колонка `PAROL_TABL_POL` с текстом «Пароль» выводит значения открытым текстом. Поле ввода — `TextField`:
```xml
<TextField fx:id="parol_pol" layoutX="426.0" layoutY="303.0" ... promptText="Введите пароль пользователя:"/>
```
В отличие от экрана входа, где используется `PasswordField`, здесь пароль отображается полностью.

**Последствия:**
- **Скомпрометирован один экземпляр приложения → скомпрометированы все пароли** (dump из heap, скриншот, shoulder-surfing, перехват обмена с БД).
- Администратор вынужден знать пароли всех — нарушение принципа минимальных привилегий.
- Пароли, вероятно, совпадают с пользовательскими паролями в других системах → повышенный ущерб при утечке.
- Нарушение ФЗ-152 и аналогичных требований при персональных данных.

**Меры снижения:**
1. Перейти на хеширование: **bcrypt** или **Argon2id** (в MySQL 8 доступна функция `SHA2()`, но она не имеет соли и подсолей — недостаточна).
   ```java
   // Регистрация
   pstmt.setString(2, BCrypt.hashpw(password, BCrypt.gensalt(12)));
   // Проверка
   BCrypt.checkpw(input, storedHash);
   ```
2. Убрать `parol` из `SELECT` в `getPolzovateli()`; заменить колонку на «Пароль изменён» (дата).
3. Заменить `<TextField fx:id="parol_pol">` на `<PasswordField>`.
4. Вынести смену пароля в отдельный экран с полями «старый / новый / повтор».
5. Ввести ограничение минимальной длины и сложности пароля.

#### R-05 · Отсутствие таймаута JDBC-соединения
**R = 4 × 4 = 16 · Категория: Устойчивость**

**Описание.** URL подключения не содержит параметров `connectTimeout` и `socketTimeout`. Значение по умолчанию — `0`, то есть **бесконечное ожидание** на уровне драйвера.

**Механизм.** `ConnectionUtil.java:18–22` — в URL присутствуют только хост, порт и имя БД. Драйвер MySQL при недоступном хосте блокируется до истечения системного таймаута TCP (в Windows — до ~2 минут при SYN без ответа, до ~2 минут 20 секунд при фильтрации пакетов).

**Последствия.** При выключенном сервере или неверном IP пользователь нажимает «Войти», окно не реагирует **минутами**. `showAlert()` не успевает сработать — он вызывается из `catch`, который не наступает. Приложение выглядит зависшим и воспринимается как сломанное. Повторные клики «Войти» запускают новые попытки подключения (см. R-07), создавая лавину диалогов.

**Меры снижения:**
```java
"jdbc:mysql://192.168.1.141:3306/toor11"
+ "?connectTimeout=5000&socketTimeout=10000&useSSL=true&requireSSL=true"
+ "&serverTimezone=UTC&allowPublicKeyRetrieval=false"
```

#### R-06 · Новое TCP-соединение на каждую операцию
**R = 5 × 3 = 15 · Категория: Производительность**

**Описание.** `ConnectDb()` вызывается безусловно в каждом из 9 методов доступа к данным. Пул соединений отсутствует.

**Механизм.** Типичный сценарий «Изменить»:
1. `updatePolzovatel()` → `ConnectDb()` — соединение №1 (TCP-хэндшейк, аутентификация, TLS)
2. `pstmt.executeUpdate()` → запись
3. `allData.setAll(ConnectionUtil.getPolzovateli())` (`TablPolz.java:100`) → `ConnectDb()` — соединение №2
4. `SELECT * FROM polzovateli` — чтение всех столбцов, включая `parol`

Один клик = два полных цикла установки соединения. Переход «Назад» → «Пользователи» → «Изменить» → «Меню» → «Товары» → «Изменить» даёт 6–8 рукопожатий.

**Последствия.**
- `max_connections` в MySQL по умолчанию 151 — при нескольких открытых экземплярах приложения возможен `Too many connections`.
- Заметная задержка на каждой операции (200–500 мс на локальной сети, 500–2000 мс по сети).
- Деградация общей производительности БД из-за постоянного создания и уничтожения соединений.

**Меры снижения:**
1. Ввести `HikariCP` (или `DriverManagerDataSource` + пул) как поле `ConnectionUtil`:
   ```java
   private static final HikariDataSource DS = new HikariDataSource(cfg); // maxPoolSize=10
   ```
2. Вызывать `DS.getConnection()` — он берёт соединение из пула и закрывается за микросекунды.
3. Ввести пакетные операции: после `INSERT/UPDATE` обновлять локальный `ObservableList` без повторного `SELECT`.

#### R-07 · Блокировка FX-потока при выполнении SQL
**R = 4 × 4 = 16 · Категория: Производительность**

**Описание.** JavaFX требует, чтобы все обращения к узлам сцены выполнялись на FX Application Thread. В проекте SQL-запросы выполняются непосредственно в обработчиках `@FXML`-методов, то есть **на FX-потоке**.

**Механизм.** `Tabltovar.java:46`:
```java
allData = ConnectionUtil.getDataUsers();   // блокирует FX-поток на время сетевого обмена
tabl_tovar.setItems(allData);
```

**Последствия.**
- На время запроса окно не перерисовывается: не работает перетаскивание, не мигает курсор, нажатия не обрабатываются → приложение «висит».
- При недоступной БД зависание длится минуты (R-05) — критично.
- Невозможно показать индикатор ожидания, отменить операцию или дать пользователю отзыв.
- При наполнении `tovar` несколькими тысячами строк интерфейс перестаёт отвечать даже при быстрой сети: `TableView` без виртуального управления создаёт `TableRow` на каждую строку.

**Меры снижения:**
1. Оборачивать SQL в `Task`/`Service`:
   ```java
   Task<ObservableList<Tablich1>> t = new Task<>() {
       protected ObservableList<Tablich1> call() { return ConnectionUtil.getDataUsers(); }
   };
   t.setOnSucceeded(ev -> tabl_tovar.setItems(t.getValue()));
   new Thread(t, "db-load").start();
   ```
2. Показать `ProgressIndicator` и кнопку «Отмена» через `t.setOnCancelled`.
3. Включить виртуализацию `TableView`:
   ```xml
   <TableView fx:id="tabl_tovar" ... >
       <columns>...</columns>
   </TableView>
   ```
   ```java
   tabl_tovar.setEditable(false);
   tabl_tovar.getStyleClass().add("tableview-cell");
   ```
   Либо ограничить объём: `SELECT ... LIMIT 1000` + пагинация.

#### R-08 · Ручной ввод первичного ключа
**R = 4 × 3 = 12 · Категория: Данные**

**Описание.** `id` вводится пользователем вручную и передаётся в `INSERT` как явное значение. Автоинкремент не используется.

**Механизм.** `ConnectionUtil.java:79`:
```java
String sql = "INSERT INTO tovar (id, name, chen) VALUES (?, ?, ?)";
```
`Tabltovar.validateFields()` (`:157–173`) проверяет только непустоту и целочисленность — уникальность не проверяется.

**Последствия.**
- `Duplicate entry 'N' for key 'PRIMARY'` — пользователь видит техническую ошибку вместо понятного сообщения (см. R-12).
- Администратор обязан вручную подбирать свободный `id`, что приводит к ошибкам и «дырявым» идентификаторам.
- Риск перезаписи: если `id` не первичный ключ, а обычный столбец, `INSERT` создаст дубликат без ошибки.

**Меры снижения:**
1. `AUTO_INCREMENT` в БД и `INSERT INTO tovar (name, chen) VALUES (?, ?)`.
2. Возвращать сгенерированный ключ: `pstmt.getGeneratedKeys()`.
3. В форме добавления поле `id` должно быть `disabled` или отсутствовать; редактирование — по выбору строки.

#### R-09 · Отсутствие уникальности логина и обработки дублей
**R = 4 × 3 = 12 · Категория: Данные**

**Описание.** `INSERT INTO polzovateli (id, name, family, login, parol)` не проверяет, существует ли уже пользователь с таким `login`.

**Последствия.**
- Два пользователя с одинаковым `login` и разными паролями → `authorize()` вернёт `USER` при входе с **любым** из паролей. Аккаунт перестаёт быть идентифицирующим.
- Ошибка БД при попытке создать дубль (если `UNIQUE` есть) обрабатывается только как общий текст ошибки.
- Администратор не может понять, какому сотруднику принадлежит конкретная учётная запись.

**Меры снижения:**
1. `ALTER TABLE polzovateli ADD UNIQUE KEY uq_login (login);`
2. Предварительная проверка:
   ```java
   if (loginExists(p.getLogin(), null)) { showInfo("Логин уже занят"); return false; }
   ```
3. Обработка `SQLIntegrityConstraintViolationException` с понятным сообщением.

#### R-11 · Разграничение доступа реализовано только на клиенте
**R = 3 × 4 = 12 · Категория: Безопасность**

**Описание.** Роль определяется в Java-коде и передаётся в БД тем же соединением. Ограничения на уровне SQL отсутствуют.

**Механизм.** `Session.java:4–5`:
```java
public static String currentUser = null;
public static String role = null;
```
Проверки `Session.isAdmin()` расставлены в трёх слоях: контроллере (`TablPolz.java:40`, `Tabltovar.java:58`), в модели доступа (`ConnectionUtil.addUser()` и др.) и в `Menu.pol_button()`. Все три работают с одним и тем же статическим полем.

**Последствия.**
- Любой, кто изменит `Session.role = "ADMIN"` (отладчик, декомпиляция, патч байткода), получает все права. В модели «приложение + общая БД» это реалистичный сценарий.
- Учётная запись `USER`, созданная администратором, равноправна админу при компрометации клиента.
- Роли нет в БД — невозможно добавить третью роль (`MANAGER`) без изменения кода.
- Статические поля — общеизвестное состояние, не потокобезопасно; `Session` используется из обработчиков, которые JavaFX сериализует на FX-потоке, поэтому гонки маловероятны, но при переходе на `Task` (см. R-07) появится реальный риск.

**Меры снижения:**
1. Добавить `role` в БД и возвращать роль из `authorize()`.
2. Перейти на инкапсуляцию: `private static volatile String role` + геттер, убрать публичную мутабельность.
3. Управлять правами на уровне БД:
   ```sql
   CREATE USER 'user_ro'@'%' IDENTIFIED BY '...';
   GRANT SELECT ON toor11.tovar TO 'user_ro'@'%';   -- только чтение товаров
   ```
   Выбор соединения — по роли из `Session`.
4. Добавить таймаут сессии и повторную авторизацию при истечении.

#### R-13 · Отсутствие логирования и аудита
**R = 4 × 3 = 12 · Категория: Эксплуатация**

**Описание.** Единственная диагностика — `System.err.println` и модальные окна. Журналирования действий пользователей нет.

**Механизм.** `ConnectionUtil.java:24–29` — вывод в консоль:
```java
System.err.println("Ошибка подключения: " + e.getMessage());
showAlert("Ошибка подключения", "Не удалось подключиться к БД: " + e.getMessage());
```
Если приложение запущено из `javafx:run` или как `.jar` без перенаправления, эти сообщения **теряются**. В `javafx-maven-plugin` настроен `launcher=app`, но не задан вывод в файл.

**Последствия.**
- **Невозможно установить, кто и когда удалил товар или изменил пароль.** При расхождении учётных данных ответственность не установить.
- Диагностика инцидентов требует воспроизведения — потеря времени.
- Ошибки БД не попадают в системный журнал, администратор их не увидит.

**Меры снижения:**
1. Подключить `java.util.logging` или SLF4J + Logback.
2. Конфигурация `logback.xml`: файлы `%d{yyyy-MM-dd HH:mm:ss} %-5level [%thread] %logger{36} - %msg%n` + ротация по размеру.
3. **Аудит-таблица в БД:**
   ```sql
   CREATE TABLE audit_log (
       id INT AUTO_INCREMENT PRIMARY KEY,
       ts TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
       username VARCHAR(64),
       action VARCHAR(16),      -- INSERT/UPDATE/DELETE/AUTH
       entity VARCHAR(32),
       entity_id INT,
       details TEXT
   );
   ```
   Запись в той же транзакции, что и изменение.
4. Файл лога — в `%LOCALAPPDATA%\Repetich\logs` (не в рабочий каталог, доступный другим пользователям).

#### R-15 · Конфликт версий JDK, JavaFX и namespace FXML

#### R-27 · Привязка к домашнему сетевому адресу
**R = 5 × 3 = 15 · Категория: Инфраструктура**

**Описание.** `192.168.1.141` — адрес из частного диапазона RFC 1918. Он назначается DHCP-сервером и **может измениться** при перезагрузке роутера или смене устройства.

2. Для локальной разработки — `localhost` или `127.0.0.1` с контейнером (R-14).
3. Добавить в `README.md` раздел «Требования к БД» с указанием IP, порта, схемы и прав.

#### R-10 · Отсутствие валидации длины и формата полей
**R = 4 × 2 = 8**

**Описание.** `validateFields()` проверяет только непустоту и целочисленность `id`. Длина строк, формат цены, допустимые символы не проверяются.

**Механизм.** `Tabltovar.java:157–173`:
```java
private boolean validateFields() {
    if (id_tovar.getText().trim().isEmpty()
            || naz_tovar.getText().trim().isEmpty()
            || chen_tovar.getText().trim().isEmpty()) { ... }
    try { Integer.parseInt(id_tovar.getText().trim()); }
    catch (NumberFormatException e) { ... }
    return true;      // ← ни одной проверки больше
}
```
Цена хранится в `VARCHAR` (комментарий `Tablich1.java:5`: `// VARCHAR в БД`). Введя `abc`, пользователь получит `Data truncation` от MySQL.

**Последствия:** невалидные данные в БД, ошибки при сортировке и расчётах, порча таблицы.

**Меры:** проверить формат цены (`^-?\d+([.,]\d{1,2})?$`) до вставки; привести `chen` к `DECIMAL(10,2)` в схеме; ограничить длину `TextField` через `<TextField fx:id="..."><font>…</font></TextField>` + `TextFormatter` или слушатель.

#### R-12 · Утечка внутренней информации через сообщения об ошибках
**R = 4 × 2 = 8**

**Описание.** Сырые `e.getMessage()` из JDBC выводятся в модальные окна и на экран.

**Механизм.** `ConnectionUtil.java:27–28`:
```java
showAlert("Ошибка подключения", "Не удалось подключиться к БД: " + e.getMessage());
```

Типичные сообщения MySQL раскрывают: `Access denied for user 'toor11'@'192.168.1.5'`, `Unknown database 'toor11'`, `Communications link failure`, внутренний порт и путь драйвера.

**Последствия.** Пользователь получает бесполезную техническую информацию; при демонстрации работы на экране видны имя БД и логин. Номер `e.getMessage()` невозможно диагностировать (нет кода, нет стека).

**Меры:** пользователю — нейтральное сообщение с кодом инцидента; в лог — полный `e` со стеком (`LOG.log(Level.SEVERE, "DB_ERROR", e)`).

#### R-17 · `Alert.showAndWait()` в `initialize()` до отображения сцены
**R = 3 × 3 = 9**

**Описание.** `TablPolz.java:40–47`:
```java
@FXML
void initialize() {
    if (!Session.isAdmin()) {
        Alert a = new Alert(Alert.AlertType.WARNING);
        a.setContentText("Доступ только для администратора");
        a.showAndWait();      // ← до stage.show()
        return;
    }
```
`initialize()` вызывается `FXMLLoader` **внутри** `loader.load()`, то есть **до** `stage.setScene(...)` и `stage.show()` в `Menu.openScene()` (`Menu.java:51–55`). Модальный диалог создаётся в момент, когда его владелец ещё не отображён.

**Последствия.** На части конфигураций (особенно при `-Dglass.platform=Monocle`, headless CI, Linux/Wayland) — `IllegalStateException` или «зависшее» окно. Проверка роли продублирована в `Menu.pol_button()`, поэтому практическая эксплуатация затруднена, но дефект остаётся.

**Меры:** проверять роль **до** `loader.load()` в вызывающем коде; в `initialize()` — молча инициализировать пустую таблицу без диалога.

#### R-18 · `allData` остаётся `null` при отказе в `TablPolz`
**R = 3 × 2 = 6**

**Описание.** После раннего `return` в `TablPolz.java:46` поле `allData` (`TablPolz.java:37`) не инициализировано.

**Последствия.** `Poisk` (`TablPolz.java:121`) обращается к нему без проверки:
```java
for (Polzovatel p : allData) { ... }   // NPE, если allData == null
```
Путь недостижим при текущей логике меню, но это **мина на будущее**: любое изменение навигации активирует дефект.

**Меры:** `private ObservableList<Polzovatel> allData = FXCollections.observableArrayList();` — инициализация при объявлении.

#### R-19 · Получение `Stage` из элемента управления
**R = 2 × 3 = 6**

**Описание.** `Menu.java:54`:
```java
Stage stage = (Stage) tov.getScene().getWindow();   // «Берём окно из любой доступной кнопки»
```
Каждый контроллер аналогично берёт `Stage` из своей кнопки (`Tabltovar.java:141`, `TablPolz.java:144`, `HelloController.java:66`).

**Последствия.** Хрупкая связь: если `tov` не инжектирован — NPE. Ситуация возможна при частичной загрузке FXML или в тесте. При добавлении новой кнопки код придётся править «вокруг» неё.

**Меры:** внедрить общий контроллер сцены (см. R-22) либо передавать `Stage` через конструктор; альтернатива — `voti.getScene().getWindow()` только в точке входа.

#### R-20 · `System.exit(0)` вместо `Platform.exit()`
**R = 3 × 2 = 6`

**Описание.** Завершение приложения в четырёх местах: `HelloController.java:35`, `Menu.java:46`, `TablPolz.java:153`, `Tabltovar.java:149`.

**Последствия.**
- Немедленное завершение без вызова `stop()` — не выполняются обработчики завершения.
- Нет подтверждения: одно нажатие на «Выход» уничтожает несохранённый ввод в форме.
- Невозможно перехватить завершение для очистки сессии или ресурсов.

**Меры:** `Platform.exit()` + `Platform.setImplicitExit(false)`; подтверждение `Alert.AlertType.CONFIRM` при наличии несохранённых изменений.

#### R-21 · Отсутствие транзакций и десинхронизация UI
**R = 3 × 3 = 9**

**Описание.** После каждой операции выполняется полная перезагрузка данных:
`Tabltovar.java:80, 96, 107`; `TablPolz.java:82, 100, 111`:
```java
allData.setAll(ConnectionUtil.getDataUsers());
```
Операция не размечена транзакцией; `autoCommit` по умолчанию — `true`.

**Последствия.**
- Состояние `TableView` может расходиться с БД: если перезагрузка вернёт пустой список (ошибка), `allData.setAll(empty)` **затрёт** корректно отображавшиеся данные, и пользователь решит, что база пуста.
- Нет промежуточных обновлений — лишний полный `SELECT` (см. R-06).
- При параллельной работе двух администраторов изменения одного видны другому только после ручного обновления.

**Меры:** обновлять локальный список точечно (`allData.add(t)` / удаление по индексу) вместо повторного `SELECT`; проверять результат загрузки перед `setAll`; явно задавать `autoCommit(false)` и вызывать `commit()`/`rollback()`.

#### R-22 · Ложные имена методов
**R = 4 × 2 = 8**

**Описание.** `ConnectionUtil.getDataUsers()`, `addUser()`, `updateUser()`, `deleteUser()` (`ConnectionUtil.java:54, 79, 98, 117`) оперируют **товарами** (`tovar`), а не пользователями. Параллельно существует корректная пара `getPolzovateli()` / `addPolzovatel()`.

**Последствия.** Высокая вероятность ошибки при доработке — вызов `deleteUser()` для удаления товара. В текущем коде вызовы корректны, но семантическая нагрузка на разработчика непрозрачна.

**Меры:** переименовать в `getTovary()`, `addTovar()`, `updateTovar()`, `deleteTovar()`.

#### R-26 · Нет глобального обработчика необработанных исключений
**R = 3 × 3 = 9**

**Описание.** Единственная защита — `Thread.setDefaultUncaughtExceptionHandler` (не установлен) и try/catch в `initialize()`-методах. Любое необработанное исключение завершает приложение.

**Последствия.** R-01 — прямое следствие: NPE из `authorize()` не перехватывается и убивает приложение. То же для NPE в `Tabltovar.initialize()` (`:63–65`, если `id_tovar` не инжектирован) и в `Menu.openScene()`.

**Меры (R-26 + частично R-01):**
```java
@Override
public void start(Stage stage) {
    Thread.setDefaultUncaughtExceptionHandler((t, e) -> {
        LOG.log(Level.SEVERE, "Необработанная ошибка в потоке " + t.getName(), e);
        new Alert(Alert.AlertType.ERROR,
                  "Непредвиденная ошибка", e.getMessage()).show();
    });
    // ...
}
```

#### R-28 · Отсутствие ограничений ссылочной целостности
**R = 3 × 3 = 9**

**Описание.** В SQL нет ни `NOT NULL`, ни `UNIQUE`, ни `FOREIGN KEY`, ни `CHECK`. Схема БД неизвестна (R-14), поэтому наличие ограничений установить нельзя.

**Последствия.** Пользователь без логина, товар с пустой ценой, дубликаты `id` — всё попадает в БД. Если ограничения есть, нарушение приводит к необработанному `SQLException` (см. R-10).

**Меры:** описать ограничения в `schema.sql` (R-14), добавить `CHECK (chen > 0)` после перевода на `DECIMAL`.

---

#### R-29 · Нет защиты от удаления собственной учётной записи
**R = 3 × 2 = 6**

**Описание.** `TablPolz.udal_pol()` удаляет пользователя по введённому `id` без проверки, не является ли он текущим.

**Последствия.** Администратор может удалить себя. Учётная запись `admin` в коде сохранится (R-02), но при переходе на БД-роли (R-11) система останется без администратора.

**Меры:** блокировать удаление `id`, равного `Session.currentUserId`, либо требовать подтверждения: «Вы уверены, что хотите удалить собственный аккаунт?»

## 9. Рекомендация

**Проект не готов к приёмке в текущем виде.**

Блокером является не архитектурное решение, а **концентрация дефектов в одном классе** `ConnectionUtil.java`, где в 9 методах повторяется некорректный шаблон `try-with-resources` с потенциально `null`-ресурсом (R-01). Устранение этого дефекта — порядка 40 строк кода — снимает риск уровня «Критический» и одновременно открывает путь к тестируемости через выделение `Repository`.

Рекомендуемый порядок: **P0 (6 мероприятий) → P1 (8 мероприятий) → повторная оценка рисков**. Ожидаемое снижение интегрального риска после P0+P1 — с **341** до **178** (−48%).
